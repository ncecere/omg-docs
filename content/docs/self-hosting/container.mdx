## The image

The repository's `Dockerfile` builds everything into one small image:

1. Node builds the dashboard.
2. Rust builds the `open-model-gateway` binary (with `--locked`); migrations are compiled into it.
3. A distroless runtime (`gcr.io/distroless/cc-debian12`, pinned by digest) holds the binary, the built dashboard in `/app/web`, the C runtime libraries and CA certificates. Nothing else: no shell, package manager, `curl`, Node or Cargo.

From v0.3.1 the image is about 25 MB compressed (it was 52 MB on the Debian slim base of earlier releases).

### Release images

From v0.3.0, each release publishes a signed image to `ghcr.io/ncecere/open-model-gateway`, under three tags:

| Tag | Points to |
|---|---|
| `vX.Y.Z`, such as `v0.6.0` | That release. |
| `vX.Y`, such as `v0.6` | The newest patch release of that minor version. |
| `latest-release` | The newest release. |

Images are signed with cosign keyless signing from the repository's GitHub Actions workflow. Check the signature with **cosign v3.0 or newer** (cosign v2 reports "no signatures found": from v0.4.0, signatures are stored in cosign v3's bundle format), then pin the image by its digest:

```sh
cosign verify ghcr.io/ncecere/open-model-gateway@sha256:49b4f2dbe2777060a82c9567431d5e3fe757244dc9ffb968ff75a15ba8787393 \
  --certificate-identity https://github.com/ncecere/open-model-gateway/.github/workflows/image.yml@refs/tags/v0.6.0 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

The tags move; a digest doesn't. Promote the digest you tested, and roll back to a previous digest, never to a rebuilt tag:

```sh
docker pull ghcr.io/ncecere/open-model-gateway:v0.6.0@sha256:49b4f2dbe2777060a82c9567431d5e3fe757244dc9ffb968ff75a15ba8787393
```

Before publishing, release images are scanned for known vulnerabilities (fixable high and critical findings block the release) and get an SBOM and build provenance. See [Security](/docs/self-hosting/security#how-releases-are-checked).

### Build it yourself

```sh
git clone https://github.com/ncecere/open-model-gateway.git
cd open-model-gateway
git checkout v0.6.0        # the release you want
docker build -t open-model-gateway:v0.6.0 .
```

The repository's manual publishing workflow also pushes a tested image of `main` to `ghcr.io/ncecere/open-model-gateway`, tagged with the full commit SHA, for staging.

| Property | Value |
|---|---|
| User | `10001:10001`, non-root |
| Port | `8080` (`GATEWAY_LISTEN=0.0.0.0:8080`) |
| Defaults | `GATEWAY_ENV=production`, `GATEWAY_WEB_DIR=/app/web` |
| Entrypoint | `/usr/local/bin/open-model-gateway`, the gateway binary itself |
| Command | `serve` by default; any other subcommand can be passed after the image name |
| Health check | `open-model-gateway healthcheck --timeout 3s` every 30 seconds (exec form) |
| Writable paths | None needed: runs with a read-only root filesystem |

## Startup and secrets

The image has no shell and no entrypoint script: the binary is PID 1 and handles `SIGTERM` itself. Before it reads any configuration, it:

- sets a strict umask (`077`);
- reads four secrets from files if you set their `_FILE` companion: `DATABASE_URL_FILE`, `GATEWAY_OIDC_CLIENT_SECRET_FILE`, `OPENAI_API_KEY_FILE` and `ANTHROPIC_API_KEY_FILE`. The file must be a readable regular file (symlinks, as in Kubernetes secret mounts, are fine); one trailing newline is removed;
- refuses to start if a variable and its `_FILE` are both set, or if one of those four values is empty, longer than 4,096 bytes, or contains a line break or NUL. The error names the variable and the reason, never the value or the file's path.

Other `_FILE` variables aren't read, so pass other secrets (for example a provider key with another name) as environment variables. The binary does this for every command except `healthcheck`, in a container or not.

It runs exactly the command you give it and **never migrates the database or creates users** by itself; those are explicit, one-off commands:

```sh
# One-off: create or upgrade the schema, as the migrator role.
docker run --rm -e DATABASE_URL_FILE=/run/secrets/migrator_url \
  -v ./secrets:/run/secrets:ro ghcr.io/ncecere/open-model-gateway:v0.6.0@sha256:49b4f2dbe2777060a82c9567431d5e3fe757244dc9ffb968ff75a15ba8787393 migrate

# One-off: name the first Platform Admin.
docker run --rm -e DATABASE_URL_FILE=/run/secrets/migrator_url \
  -v ./secrets:/run/secrets:ro ghcr.io/ncecere/open-model-gateway:v0.6.0@sha256:49b4f2dbe2777060a82c9567431d5e3fe757244dc9ffb968ff75a15ba8787393 \
  provision-user --email morgan.lee@example.edu --platform-admin
```

After every `migrate`, also run `grants apply` the same way, as the migrator, to reapply the runtime role's grants.

Other one-off commands you're likely to run in a container:

| Command | Does |
|---|---|
| `grants apply` | Applies the runtime role's grants (`deploy/staging/runtime-grants.sql`, embedded in the binary), as the migrator. Run it after every `migrate`. From v0.5.0. |
| `grants verify` | Checks the runtime role's privileges with probes that roll back. Needs a role that can `SET ROLE gateway_runtime`. From v0.5.0. |
| `wait-for-database [--schema] [--timeout-seconds N]` | Waits until PostgreSQL accepts connections (with `--schema`, until this binary's schema and grants are in place), then exits 0; exits 1 after the timeout (600 s by default). For init containers. From v0.5.0. |
| `files verify` | Compares stored-file records with the file store; also reports the active encryption key and any retired keys still in use. |
| `files rekey --from <old> --to <new> [--dry-run]` | Re-wraps every stored file's data key under another master key, so the old key can be removed. Resumable, and safe while the gateway serves. From v0.6.0. See [File storage](/docs/self-hosting/file-storage). |
| `budget verify`, `history verify` | Read-only consistency checks; each exits nonzero on a finding. |

<Callout title="Upgrading from v0.3.0 or earlier">
  Images before v0.3.1 started through a shell script, `container-entrypoint`. Remove any `--entrypoint container-entrypoint` override: arguments after the image name go straight to the binary. Replace health checks that use `sh`, `curl` or `wget` with the exec form below.
</Callout>

## Health checks

`open-model-gateway healthcheck` asks the gateway's `/health/ready` over loopback and exits 0 for a `2xx` answer, 1 for anything else (an error status, a redirect, a refused connection or a timeout). By default it uses the port in `GATEWAY_LISTEN`. It reads no configuration or secrets, ignores proxy variables, never follows redirects and refuses non-loopback addresses unless you add `--allow-non-loopback`.

```sh
open-model-gateway healthcheck [--url http://127.0.0.1:8080/health/ready] [--timeout 3s] [--allow-non-loopback]
```

The image's own `HEALTHCHECK` already runs it. To set your own in Compose, use the exec form (there is no shell for `CMD-SHELL`):

```yaml
healthcheck:
  test: ["CMD", "/usr/local/bin/open-model-gateway", "healthcheck"]
  interval: 30s
  timeout: 5s
  start_period: 20s
```

In Kubernetes, use HTTP probes: `/health/live` for liveness and `/health/ready` for readiness, on port 8080.

```yaml
livenessProbe:
  httpGet: { path: /health/live, port: 8080 }
readinessProbe:
  httpGet: { path: /health/ready, port: 8080 }
  periodSeconds: 10
```

If a probe has to be an exec probe, use `command: ["/usr/local/bin/open-model-gateway", "healthcheck"]`, never `sh -c` or `curl`. See [Metrics and monitoring](/docs/self-hosting/metrics-and-monitoring#health-checks) for what readiness checks.

### Debugging without a shell

- `docker exec CONTAINER /usr/local/bin/open-model-gateway healthcheck` (or any other subcommand, such as `budget verify`);
- `docker logs` for the JSON logs, and `docker inspect` for the user, mounts and health-check history;
- a debug container that shares the gateway's namespaces (`docker debug`, or `kubectl debug --target`) when you need tools.

## Run it hardened

The container is built to run with:

- a read-only root filesystem (it needs no writable path; the staging setup still mounts a small `/tmp` tmpfs);
- all Linux capabilities dropped and `no-new-privileges`;
- a stop grace period longer than the request deadline (the staging setup uses 150 seconds for a 120-second deadline), so requests in flight can finish and settle.

## Compose

The repository's staging setup (`deploy/staging/` and `scripts/staging.py`) is a single-host reference: PostgreSQL 17 on an internal network, separate migrator and runtime roles with file secrets, one-off `migrate` and `grant-runtime` services (the latter runs `grants apply`), the gateway, and Caddy terminating HTTPS. `staging.py` generates the secrets and runs each step:

```sh
python3 scripts/staging.py init      # generate secrets and configuration (once)
python3 scripts/staging.py build
python3 scripts/staging.py db
python3 scripts/staging.py migrate   # migrate, then grants apply
python3 scripts/staging.py up
python3 scripts/staging.py verify
```

It starts on `https://localhost:18443` with Caddy's local certificate authority and single sign-on off. For a real hostname, set `GATEWAY_HOST`, `GATEWAY_PUBLIC_URL` and the bind address and ports in the generated `.local/staging/staging.env`, then enable OIDC (see [Identity setup](/docs/self-hosting/identity)).

The shape of the gateway service, if you write your own Compose file:

```yaml
services:
  gateway:
    image: ghcr.io/ncecere/open-model-gateway:v0.6.0@sha256:49b4f2dbe2777060a82c9567431d5e3fe757244dc9ffb968ff75a15ba8787393
    read_only: true
    tmpfs: ["/tmp:rw,noexec,nosuid,size=32m"]
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]
    stop_grace_period: 150s
    environment:
      DATABASE_URL_FILE: /run/secrets/runtime_database_url
      GATEWAY_PUBLIC_URL: https://ai.example.edu
      GATEWAY_OIDC_ISSUER: https://login.example.edu
      GATEWAY_OIDC_CLIENT_ID: ai-gateway
      GATEWAY_SECRET_ENV_ALLOWLIST: OPENAI_API_KEY,ANTHROPIC_API_KEY
      OPENAI_API_KEY_FILE: /run/secrets/openai_api_key
      ANTHROPIC_API_KEY_FILE: /run/secrets/anthropic_api_key
    secrets: [runtime_database_url, openai_api_key, anthropic_api_key]
    healthcheck:
      test: ["CMD", "/usr/local/bin/open-model-gateway", "healthcheck"]
```

`init: true` is optional: the binary handles signals as PID 1.

## The reverse proxy

Put an HTTPS proxy in front of port 8080. It must:

- serve the gateway on the exact origin in `GATEWAY_PUBLIC_URL` (sign-in cookies and the `Origin` check depend on it);
- pass server-sent events through without buffering (Caddy: `flush_interval -1`);
- allow WebSocket upgrades on `/v1/realtime`;
- keep query strings, cookies and `Authorization` headers out of its access logs (sign-in callbacks carry codes);
- not expose the metrics listener.

The gateway sends no CORS headers and isn't meant to be called from other origins' pages.

## Kubernetes

From v0.4.0 there's a **beta** Helm chart for Kubernetes deployments, with an optional CloudNativePG-managed database. From v0.5.0 a first install, database and schema included, is one `helm install` with `--set migrations.run=true`. See [Kubernetes](/docs/self-hosting/kubernetes).

## Without a container

Build the binary (`cargo build --release -p open-model-gateway`) and the dashboard (`npm ci && npm run build:web`), and point `GATEWAY_WEB_DIR` at `apps/web/dist`. Keep the binary and the dashboard from the same revision. Without `GATEWAY_WEB_DIR` the gateway serves the APIs only.
