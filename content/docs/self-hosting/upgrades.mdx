---
title: Upgrades
description: The upgrade procedure, why migrations are forward-only, rolling back, and notes for each release.
---

Every release can change the database schema. The gateway never migrates itself, and replicas of different releases can't share a database, so upgrades are a short, planned procedure.

## Procedure

<Steps>
<Step>

### Read the release notes

Check the [release](/docs/releases) for migrations, new settings and grant changes. If you're skipping releases, read the notes below for each one you cross: one `migrate` with the new binary applies every migration you're missing, but each release's settings changes still apply. From v0.6.x straight to v0.10.0, follow [Skipping from v0.6.x to v0.10.0](#skipping-from-v06x-to-v0100). Build or pull the image and note its digest.

</Step>
<Step>

### Back up

Take a backup and `verify` it. For releases with migrations, run a [restore drill](/docs/self-hosting/backups-and-restore#the-restore-drill) first.

</Step>
<Step>

### Stop traffic

Stop the proxy's traffic, then every gateway replica, and pause any scheduled `open-model-gateway alerts evaluate --once` job. Mixed-release replicas are not supported, and from v0.8.0 an old replica left running can re-send alert email or break migrations ([To v0.8.0](#to-v080), [To v0.9.0](#to-v090)).

</Step>
<Step>

### Migrate and grant

As the migrator, run `open-model-gateway migrate` with the **new** binary, then `open-model-gateway grants apply`, which reapplies the runtime grants (`deploy/staging/runtime-grants.sql`, embedded in the binary). Then run `open-model-gateway grants verify` with a role that can `SET ROLE gateway_runtime`: it checks the runtime role's privileges with probes that roll back. (`python3 scripts/staging.py migrate` runs `migrate` and `grants apply`.)

`grants apply` and `grants verify` are new in v0.5.0. Before that, apply the SQL file with `psql` as the migrator, and check it with `deploy/staging/verify-privileges.sql`.

From v0.9.0, `grants apply` also revokes `TEMPORARY` on the connected database from `PUBLIC` and `gateway_runtime`, and `grants verify` tries `CREATE TEMP TABLE` as the runtime role and requires it to be refused. Give the gateway its own database: every role that relied on `PUBLIC`'s temporary-table right loses it there.

`migrate` and `grants apply` take a session-level lock, so connect them to PostgreSQL directly, never through a transaction-mode connection pooler.

</Step>
<Step>

### Start and check

Start the new release, by its verified digest. Wait for `/health/ready` to show `schema: ok`, then check the metrics, a sign-in, and one small request. After a release with migrations, run `open-model-gateway budget verify` too.

</Step>
</Steps>

### With Helm

The chart's migration Job runs `migrate` and `grants apply` with the gateway image and the migrator's credentials; it only runs when you pass `--set migrations.run=true`.

- **First install** (from v0.5.0): one command, including a chart-managed CloudNativePG cluster. The Job waits for the database (`open-model-gateway wait-for-database`), then migrates and applies the grants, and gateway pods wait for the schema (`wait-for-database --schema`) instead of crash-looping:

  ```sh
  helm install <release> deploy/helm/open-model-gateway -f <values>.yaml \
    --set migrations.run=true --wait --timeout 10m
  ```

- **Upgrades that ship a migration:** `helm upgrade … --set migrations.run=true --wait`. The Job then runs before any new gateway pod starts, but while the old ones still exist. Mixed-schema replicas aren't supported, so scale the gateway to 0 first.
- The Job applies the grants but doesn't run `grants verify`. Run it yourself with a role that can `SET ROLE gateway_runtime`.

See [Kubernetes](/docs/self-hosting/kubernetes). The chart is **beta**.

## Rolling back

- If **no migration ran**, redeploy the previous image by its digest.
- If a migration ran, restore the pre-upgrade backup **into a new database** and switch to it. There are no down migrations, and an older binary refuses a newer schema. Never run an older release's workers against the new schema.

### Skipping from v0.6.x to v0.10.0

One `migrate` with the v0.10.0 binary applies `0049` to `0068`. Do everything each release below asks for before you start, then:

1. **Prepare the configuration** while v0.6.x still runs:
   - remove reserved names from the credential allowlists ([To v0.7.0](#to-v070));
   - replace any `GATEWAY_LOCAL_UPSTREAMS` approval in a special-use range ([To v0.9.0](#to-v090)), or v0.10.0 won't start;
   - make sure nothing in front of the dashboard adds an `Authorization` header to `/api/v1/…` requests ([To v0.8.0](#to-v080));
   - leave `default_transaction_isolation` at `read committed` on the gateway's database and roles;
   - update automation that depends on management denial codes ([To v0.7.0](#to-v070), [To v0.9.0](#to-v090)).
2. **Back up**, `verify` the backup and run a restore drill.
3. **Stop every replica** and any `alerts evaluate --once` job. This covers the alert-worker rule of `0050`, the evaluator rule of `0059` and the replica rule of `0067`.
4. As the migrator: `open-model-gateway migrate`, then `grants apply`. Then `grants verify` with a role that can `SET ROLE gateway_runtime`.
5. **Start v0.10.0** by its verified digest. Wait for `/health/ready` to report `schema: ok`, then check sign-in, one small request and `open-model-gateway budget verify`.

The base image and its CA trust store changed in v0.9.1: check your outbound TLS integrations against v0.10.0 first ([To v0.9.1](#to-v091)). With chart-managed CloudNativePG, also read [To v0.9.0](#to-v090) for the database ACL change and [To v0.9.3](#to-v093) for the durability policy.

### To v0.10.0

**Migration `0068`**, with no runtime grant changes. It widens the stored result of the last email test to the delivery error categories, without rewriting data. After it, the schema has 67 migration records, the latest `0068`. Run `migrate`, then `grants apply` and `grants verify` as after every migration. Read [the release](/docs/releases/v0-10-0) first.

With Helm, chart 0.10.0 defaults `image.tag` to `v0.10.0`. Pin `image.digest` to the verified digest.

**Behaviour changes.** Input that used to fail with a `5xx` or an undocumented `409` now gets a `400`, or a recorded result:

- Control characters in list searches (`q`, and the file list's `search`), in SSO group-mapping issuers (which also refuse whitespace), and in model and catalog descriptions (tab, line feed and carriage return are still allowed). SCIM list filters with one answer `invalidFilter`.
- An identity provider groups claim containing a control character refuses the sign-in, like any malformed claim.
- List cursors (logs, sessions, holds, route history) outside PostgreSQL's date range.
- Manual cost reconciliation with incoherent token counts, or output tokens on an embeddings or rerank hold.
- An email test to a relay that isn't on `GATEWAY_SMTP_HOST_ALLOWLIST` is recorded as a failed test, `host_not_allowed`, instead of answering `409`.
- A support or logo URL's 2,048-character limit applies to its stored, percent-encoded form. A URL that normalizes to at most 2,048 characters is accepted even when what you typed was longer; a longer one is `400`.
- `/v1/embeddings` answers an oversized streamed body with the OpenAI `payload_too_large` error.

**Check before you upgrade:**

- An existing SSO group mapping whose issuer contains a control character or whitespace can't be updated until you correct the issuer. Deleting it still works.
- A catalog whose stored description contains a control character other than tab, line feed or carriage return must have its description corrected on its next update.

Also new: drift-checked OpenAPI 3.1 documents for the management API and the supported inference API ([Management API](/docs/api/management-api#openapi-documents)), and the **Provider reconciliation** view in Admin › Usage & costs ([Usage, logs and cost centers](/docs/administration/usage-logs-and-cost-centers#provider-reconciliation)).

### To v0.9.0

**Migrations `0053` to `0067`**, and new runtime grants. Read [the release](/docs/releases/v0-9-0) first: one change stops startup.

**Before you start:**

1. **Check `GATEWAY_LOCAL_UPSTREAMS`.** An approval that pins an address in one of these ranges now stops `serve` at startup, before it connects to the database (v0.8.0 only warned):

   | Range | Category |
   |---|---|
   | `198.18.0.0/15`, `2001:2::/48` | Benchmarking |
   | `192.0.0.0/24` | IETF protocol assignments |
   | `192.88.99.0/24` | Deprecated 6to4 relay |
   | `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`, `2001:db8::/32`, `3fff::/20` | Documentation |
   | `fd00:ec2::/32` (all of it, over HTTP or HTTPS) | AWS IPv6 metadata |

   An address carrying an IPv4 address (IPv4-mapped, 6to4, Teredo) is judged by that address. Approvals of public or RFC 1918 addresses aren't affected. Replace the address with the model server's real public or private address, or remove the approval. The error names the approval's host, address and category, and the setting. Only `serve` reads approvals, so `migrate` and `grants` still run. A replica that fails this way never becomes ready, so a rolling deployment keeps the old replicas.
2. **Stop every v0.8.x (or older) alert evaluator**, including any scheduled `alerts evaluate --once` job, before `0059`. An older evaluator under `0059` can fail an evaluation and miss a short-lived incident.
3. **Stop every older replica before `0067`.** An older replica that changes a route after `0067` still has its change recorded, but attributed to System, with a second history entry.
4. With **chart-managed CloudNativePG**, read [Database ACLs](/docs/self-hosting/kubernetes#database-acls) if your cluster was created before v0.9.0.

**Operator order:**

1. Record the running digest and configuration. Back up, `verify` and run a restore drill.
2. Drain and stop every old replica and any `alerts evaluate --once` job.
3. As the migrator: `open-model-gateway migrate` (`0053` to `0067`). With Helm, `helm upgrade … --set migrations.run=true --wait` runs `migrate` and `grants apply` in the pre-upgrade Job.
4. As the migrator: `open-model-gateway grants apply`.
5. `open-model-gateway grants verify`, with a role that can `SET ROLE gateway_runtime`. It now also requires that the runtime role can't `CREATE TEMP TABLE`.
6. Start v0.9.0 by its verified digest. Wait for `/health/ready` with `schema: ok`.
7. Check sign-in, one small request and `open-model-gateway budget verify`.

**Migrations to plan for:**

| Migration | What waits | Plan |
|---|---|---|
| `0055` | Holds an exclusive lock on `alert_deliveries` while it tags every pending alert email with its workspace. | Takes longer with a large email backlog: plan a window. |
| `0065` | Alters the same table and builds indexes on it in a transaction. | As `0055`. |
| `0054`, `0056`, `0060`, `0062` | Build indexes `CONCURRENTLY`, outside a transaction, and wait for older transactions to end. | An interrupted build leaves an invalid index; the next `migrate` drops and rebuilds it. |

**Breaking and behaviour changes:**

- **Local-upstream approvals in special-use ranges are refused** (above). `/health/ready`'s `checks.local_upstream_approvals` now always reports `ok` when a replica answers.
- **`TEMPORARY` is revoked** on the gateway's database from `PUBLIC` and `gateway_runtime` by `grants apply`, and `grants verify` checks it ([Migrate and grant](#migrate-and-grant)).
- **Fresh chart-managed CloudNativePG clusters restrict database access** from their first start. Existing clusters keep their access until you change it by hand ([Database ACLs](/docs/self-hosting/kubernetes#database-acls)).
- **Plain-HTTP telemetry and audit exports are loopback-only after DNS** (development only). With `GATEWAY_ENV=development`, plain-HTTP OTLP traces, metrics and operational logs, audit OTLP logs and audit webhooks connect only if every resolved address is loopback. Production never allowed plain HTTP.
- **Another person's personal workspace answers `404`** on every `/api/v1/workspaces/{ws}` route, exactly like an unknown id, including for Platform Admins and Auditors (it was `403`). Non-admins still get `403` first on Platform-Admin-only workspace writes.
- New additive fields in API responses and the audit export. Consumers that reject unknown fields need updating.

**New, optional settings:** the alert webhook allowlists `GATEWAY_ALERT_WEBHOOK_URL_ALLOWLIST` and `GATEWAY_ALERT_WEBHOOK_SECRET_ENV_ALLOWLIST`, OTLP metrics (`GATEWAY_METRICS_OTLP_*`) and OTLP operational logs (`GATEWAY_LOGS_OTLP_*`). See [Configuration](/docs/self-hosting/configuration). `GATEWAY_ALERT_INTERVAL_SECONDS=0` now also stops scheduled-report email and alert webhooks, but not report generation.

The runtime grants add column grants for key issuance limits, alert email buckets and limits, webhooks, scheduled reports and access requests, and `SELECT` and `INSERT` on route configuration history. Nothing lets the runtime role delete or rewrite history.

Also new: [scheduled cost reports](/docs/administration/usage-logs-and-cost-centers#scheduled-reports), [signed alert webhooks](/docs/administration/alerts#webhooks), [key issuance limits](/docs/administration/limits-and-budgets#key-issuance-limits) (50 keys per person and 500 per workspace in 24 hours by default), aged unknown-hold alerts and the **Holds** tab, [access requests](/docs/administration/teams-and-projects#access-requests), [route history and change review](/docs/administration/models-and-routes#route-history-and-change-review), [SSO group-mapping review](/docs/administration/sso-groups#review-changes), and Claude Code's fields on [Messages](/docs/api/messages).

### To v0.8.0

**Migrations `0049` to `0052`**, and new runtime grants. The procedure is the same from v0.7.1 or v0.7.2 (both on `0048`). Read [the release](/docs/releases/v0-8-0) first.

**Before you start:**

1. **Management requests with an `Authorization` header are refused** with `401`. If a reverse proxy, SSO gateway or anything else in front of the dashboard adds an `Authorization` header, stop it doing so for `/api/v1/…`. Inference (`/v1/…`) is unaffected.
2. **Check `GATEWAY_LOCAL_UPSTREAMS`** against the ranges in [To v0.9.0](#to-v090). v0.8.0 logs a warning for each and reports `checks.local_upstream_approvals: "warning"` on `/health/ready`, without failing readiness; v0.9.0 refuses to start.
3. **Keep `default_transaction_isolation` at `read committed`** on the gateway's database and roles. Creating an admin API token refuses any other isolation level.
4. With Helm, leave `cnpg.cluster.backup.method` alone unless you mean to switch backup methods ([Backups](/docs/self-hosting/kubernetes#backups)).

**Operator order:**

1. Record the running digest and configuration. Back up, `verify` and run a restore drill.
2. **Stop the old alert email workers before anything touches the database.** Every v0.7.x `serve` replica runs one, and so does `alerts evaluate --once`. Scale the old gateway to zero and pause any such job. If an old replica must keep running, set `GATEWAY_ALERT_INTERVAL_SECONDS=0` on it and restart it: **unsetting the variable doesn't stop the worker**, because unset means the default, 60 seconds. An old worker left running after `0050` re-sends the same alert email to every recipient on every interval.
3. As the migrator: `open-model-gateway migrate` (`0049` to `0052`). With Helm, scale to zero first, then `helm upgrade … --set migrations.run=true --wait`.
4. As the migrator: `open-model-gateway grants apply`. Without it, the new features fail at run time.
5. `open-model-gateway grants verify`.
6. Start v0.8.0 by its verified digest. Wait for `/health/ready` with `schema: ok`.
7. Check sign-in, one small request, `checks.local_upstream_approvals` and that `gateway_alert_email_deliveries` appears on the metrics listener.

`0049` changes constraints and builds indexes on `alert_events` and `api_keys`, and `0052` builds an index on every `audit_events` month partition: run them in a quiet period on a large installation.

**Behaviour changes:**

- Management routes accept exactly one credential: a browser session or an [admin API token](/docs/administration/admin-api-tokens). A duplicate `Authorization` header, or an `Authorization` header together with the session cookie, is refused before either is examined.
- Alert email is retried, up to five times in 24 hours ([Alerts](/docs/administration/alerts#email)). Old replicas don't show or send the new key-expiry reminders.
- Logs responses add `trace_id`; audit events, in the dashboard and the [audit export](/docs/self-hosting/audit-export), add `admin_token_id`. Consumers that reject unknown fields need updating.
- Addresses in `3ff0::/12` outside `3fff::/20` are no longer refused as outbound destinations.

**New, optional settings:** OpenTelemetry traces (`GATEWAY_TRACES_OTLP_URL`, `GATEWAY_TRACES_SAMPLE_RATIO`, `GATEWAY_TRACES_OTLP_HEADERS_ENV`), and the chart's `cnpg.cluster.backup.method`. Also new: [admin API tokens](/docs/administration/admin-api-tokens), key-expiry reminders, budget headroom and **Refresh** on Logs. Restoring a backup: `scripts/backup.py reapply-revocations` now also covers admin API tokens.

The runtime grants add the alert email outbox and its delivery progress columns, admin API tokens and their audit records (insert and narrow updates only), and the token helper functions.

No migrations, runtime grants or settings (schema `0048`). Replace the image. Coming from v0.6.1, first follow [To v0.7.0](#to-v070). Both are compatibility fixes; see [the API reference](/docs/api) for what they accept:

### To v0.7.0

No migrations or runtime grants (schema `0048`), but three changes can stop startup or break automation. Read [the release](/docs/releases/v0-7-0) first.

- **Reserved credential names stop startup.** `GATEWAY_SECRET_ENV_ALLOWLIST` and `GATEWAY_SMTP_SECRET_ENV_ALLOWLIST` refuse the gateway's own names, even when listed: `DATABASE_URL`, `DATABASE_URL_FILE`, every `GATEWAY_*`, `AWS_*`, `PG*` and `OTEL_*` name, the proxy variables (`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`, in either case) and every variable a gateway secret pointer selects (such as the one `GATEWAY_SCIM_TOKEN_ENV` names). Check the names, not the values, before you roll out. Give providers and SMTP their own dedicated variables, and update the connection or SMTP reference. Never copy a gateway secret into a provider variable to get round it. See [Configuration](/docs/self-hosting/configuration#reserved-names).
- **`OPENAI_API_KEY` and `ANTHROPIC_API_KEY`** stay usable on the provider list, with a startup warning, but never on the SMTP list.
- **Management denial codes change** ([Management API](/docs/api/management-api#denial-responses)). Review automation that depends on them.
- **Local approvals:** an HTTPS approval of a 6to4 or Teredo IPv6 address is judged by the IPv4 address inside it. Embedded metadata or link-local addresses are refused, and embedded loopback works only in development. An approval that fails validation stops startup.
- **Model names** with control characters, or longer than 2,704 bytes, answer `404 model_not_found` without a database lookup. Provider job and file ids made only of dots are refused.

New, optional: `GATEWAY_INFERENCE_BASE_URL` (Helm `gateway.inferenceBaseUrl`), the inference address shown to people when inference has its own host ([Configuration](/docs/self-hosting/configuration#core)).

### To v0.6.1

- No migrations, settings or API changes. Replace the image.
- A security fix for every outbound TLS connection: the bundled roots no longer include `emSign ECC Root CA - G3`, and certificate chains through the distrusted emSign intermediates are refused (RUSTSEC-2026-0381, RUSTSEC-2026-0382).

### To v0.6.0

**Migrations `0038` to `0048`**, and new runtime grants. Read [the release](/docs/releases/v0-6-0) first: several changes stop email, sign-in, storage or clients until you act.

**Before you upgrade**, set these in your deployment:

- **`GATEWAY_SMTP_SECRET_ENV_ALLOWLIST`** (Helm `gateway.smtpSecretEnvAllowlist`): move your SMTP password variable's name here from `GATEWAY_SECRET_ENV_ALLOWLIST`. The SMTP password no longer resolves from the provider list, and a name on both lists stops startup. Until you move it, invitations and alerts aren't emailed. If a provider key was ever used as an SMTP password, rotate it.
- **`GATEWAY_SMTP_HOST_ALLOWLIST`** (Helm `gateway.smtpHostAllowlist`): list your SMTP relay host, or email stops with `host_not_allowed`.
- **`GATEWAY_EGRESS_PRIVATE_ALLOW`**: list the private networks the gateway must reach (RFC 1918, `100.64.0.0/10` including Tailscale, IPv6 unique-local), such as a private identity provider, S3-compatible store or Bedrock endpoint. Without it, startup (for sign-in) or those requests fail with a message naming the setting. List only the addresses you use. Loopback is allowed only with `GATEWAY_ENV=development`.
- **`GATEWAY_TRUSTED_PROXIES`** (Helm `gateway.trustedProxies`): your reverse proxy's addresses. Without it, every user shares the proxy's sign-in rate budget (60 a minute per replica by default).
- **Session limits:** dashboard sessions now end after 2 hours idle, as well as 12 hours after sign-in. To change that, set `GATEWAY_SESSION_IDLE_TIMEOUT` and `GATEWAY_SESSION_LIFETIME` (Helm `gateway.sessionIdleTimeout`, `gateway.sessionLifetime`).
- **Kubernetes:** the chart's NetworkPolicy has never opened SMTP or syslog ports; add a `networkPolicy.egress.extraEgress` rule for them. New optional values `networkPolicy.egress.httpsCidrs` or `httpsExceptCidrs` narrow outbound HTTPS.

**Breaking changes:**

- **Files, batches and videos in Teams and Projects are per user** (`0038`). Existing shared workspaces become **Per user**: a member's keys see only objects created with that member's keys, and other reads return `404`. Workspace owners and admins and service-account keys still see everything. For shared automation, set Workspace › Settings › General to Workspace-wide, or use a service-account key. See [Workspace settings](/docs/using/workspace-settings).
- **Revocations are final** (`0039`). Clearing or changing `revoked_at` on keys, grants, sessions or invitations fails for every role, so hand-written SQL that "un-revokes" now fails; issue a new one instead.
- **Security headers.** The dashboard can't be framed and refuses inline scripts, so a proxy that injects scripts into it no longer works.
- **The sign-in client ignores `HTTP_PROXY`, `HTTPS_PROXY` and `ALL_PROXY`**: the gateway must reach the identity provider directly.
- The SMTP, outbound-address and session changes above.

**Locks to plan for.** Most migrations in this range are small (`0038` adds a column with a constant default, without rewriting `workspaces`). These need a plan:

| Migration | What waits | Plan |
|---|---|---|
| `0041` | Rewrites `browser_sessions` under a full table lock: every dashboard request and sign-in waits until it finishes. Inference is unaffected. | Sessions were never deleted before this release. Check `SELECT count(*) FROM browser_sessions` first, and plan a short window for a large table. |
| `0040` | Builds an index on `oidc_login_attempts`: sign-in waits while it builds. | Sign-in attempts were never deleted either; expect it to take longer on an old installation. |
| `0043` | Backfills sign-in times while holding row locks on `users`: admissions of the affected users' keys wait until it commits. | Traffic is already stopped in the procedure. |
| `0047` | Builds two indexes on every `audit_events` month partition: audit writes wait while they build. | Takes a while on a large audit log. |
| `0042`, `0048` | Use a 10 s lock timeout instead of queueing behind a long transaction. | If either times out, run `migrate` again. |

From this release, the gateway's hourly maintenance deletes sessions that ended more than 30 days ago, at 10,000 rows an hour, so a large sessions table shrinks gradually. Expired sign-in attempts are deleted every minute.

**Procedure:**

1. **Back up** with `scripts/backup.py` and run `verify`.
2. **Set the allowlists** above in your deployment.
3. **Stop every gateway replica.** Mixed-schema replicas aren't supported.
4. Run `open-model-gateway migrate` as the migrator.
5. Run `open-model-gateway grants apply`, then `grants verify`. This range adds grants for sessions, legal holds, invitations, the audit export queue and state, and `stored_files.encryption_key_id`.
6. Start the new replicas and wait for `/health/ready`.
7. Send a test from Admin › Settings › Email, and sign in.

With Helm, upgrade with `--set migrations.run=true` and the new values above.

New in this release: if you ever restore a backup, run `scripts/backup.py reapply-revocations` afterwards, so access removed after the backup stays removed. See [Backups and restore](/docs/self-hosting/backups-and-restore).

During a rolling upgrade, a replica still on v0.5.0 can deliver audit events without `seq`; if you turn on [audit export](/docs/self-hosting/audit-export), start gap checks on the receiver after the upgrade.

### To v0.5.0

**Migration `0037`**, which adds two indexes for per-user lookups and no grants. Reapply the grants anyway, as after every migration. Read [the release](/docs/releases/v0-5-0) first.

**Breaking changes:**

- **Messages streaming usage.** With `stream: true`, `message_start` now comes at once with `usage: {"input_tokens": 0}` as a placeholder; the observed counts arrive in `message_delta`. A client that reads usage only from `message_start` now sees 0.
- **Responses streaming events.** Text now arrives as `response.output_text.delta` events as it's generated, instead of all at the end. Tool calls still arrive whole, after the text.
- **Slow dashboard lists return `503`** after 10 s, instead of holding up other admin requests.
- **Person pickers search on the server** and show the first 20 matches. People who are already members aren't listed.
- **Helm values:** `migrations.grants.image` is removed (the gateway image applies the grants); `cnpg.cluster.backup.destinationPath` is removed, so put `destinationPath` inside `cnpg.cluster.backup.barmanObjectStore`; the loadtest profile's `loadtest.loadgen.requests` and `concurrency` are replaced by `rate`, `duration`, `warmup`, `keys` and `extraArgs`; `cnpg.cluster.smartShutdownTimeout` defaults to `15`.

**Procedure:**

1. **Back up** with `scripts/backup.py` (now optionally encrypted with `--encrypt-to`) and run `verify`.
2. **Stop every gateway replica.**
3. Run `open-model-gateway migrate` as the migrator.
4. Run `open-model-gateway grants apply` as the migrator, then `open-model-gateway grants verify` with a role that can `SET ROLE gateway_runtime`. They replace applying `deploy/staging/runtime-grants.sql` by hand, and the chart's migration Job now runs `grants apply` too.
5. Start the new replicas and wait for `/health/ready`.

With Helm, a first install with `--set migrations.run=true` is now one step (see [With Helm](#with-helm)); upgrades that ship a migration still use `--set migrations.run=true`.

### To v0.4.0

**Migrations `0024` to `0036`**, the largest range since v0.1.0. Read [the release](/docs/releases/v0-4-0) before you upgrade: there are three breaking changes. Procedure:

1. **Back up** and verify it (`scripts/backup.py`). If you're upgrading from before `0033`, your existing backups are fine — only the *restore* path had a bug, and only for databases with reservations.
2. **Stop every gateway replica.** Mixed-schema replicas aren't supported, and three migrations briefly freeze history writes.
3. For a large installation, run `open-model-gateway partitions prepare` as the migrator **before** this maintenance window, so the heavy index builds happen online ahead of the drain.
4. Run `open-model-gateway migrate` as the migrator. Every step is resumable: an interrupted `migrate` picks up where it stopped.
5. **Reapply `deploy/staging/runtime-grants.sql`** (or let the Helm chart's migration job do it; see [Kubernetes](/docs/self-hosting/kubernetes#migration-job-and-runtime-grants)). This range adds several new grants — reapply the whole file even if some migrations add none.
6. Run `deploy/staging/verify-privileges.sql` to confirm the runtime role has exactly the expected privileges.
7. Run `open-model-gateway budget verify` (expect `mismatch_count: 0`, `rate_mismatch_count: 0`) and `open-model-gateway history verify` (expect `finding_count: 0`).
8. Start the new replicas, wait for `/health/ready`, then check sign-in and one bounded request.

- **Breaking: installation-wide budgets and rate limits are removed** (`0026`). Limits now exist only on workspace-type defaults, platform overrides, workspace caps and keys. `GET`/`PUT /platform/installation/policy` return `410 installation_limits_removed`. Any installation budget alert rule becomes a non-blocking **Installation spend** rule, keeping its thresholds and recipients. Move any shared ceiling you relied on into type defaults, overrides or keys before upgrading; workspaces may use more in total afterward.
- **Breaking: a budgeted request on an unbounded price returns `503 price_unbounded`, not `429 budget_exceeded`.** Unchanged from v0.3.2, repeated here because the admission path it runs through is rewritten this release.
- **Breaking: workspaces, keys, routes and cost centers can no longer be deleted, truncated or re-keyed, by any role** (`0034`). The product never did this — it disables, revokes and archives — so this mainly affects hand-written operator SQL, which now fails with a named check instead of a generic foreign-key error.
- Eight new environment variables, all optional with unchanged defaults: see [Configuration](/docs/self-hosting/configuration#scaling).
- New ids (requests, attempts, ledger entries, audit events) are UUIDv7 instead of UUIDv4: `x-request-id` values change shape, not format.
- A Kubernetes Helm chart is new and **beta**; see [Kubernetes](/docs/self-hosting/kubernetes).

See [Scaling](/docs/self-hosting/scaling) for what replicas, caches and partitions change in how the gateway runs.

### To v0.3.2

- No migrations and no new runtime grants. Rolling back to v0.3.1 is a redeploy of its digest.
- Routes on connections that can't serve their model are no longer accepted (`400 route_unsupported_capability`), but existing ones are kept. After upgrading, open Admin › Models and filter by **Not serving**; for each model, add a route on a connection that serves it and disable the unsupported route. See [Routes must be servable](/docs/administration/models-and-routes#routes-must-be-servable).
- Prices published through the management API must state every meter (`400 price_meters_incomplete`). Scripts that publish prices must add the missing meters as priced, not applicable or `unknown`.
- Budgeted requests on a price that can't bound them now get `503 price_unbounded` instead of `429 budget_exceeded`. Update alerts or dashboards that counted them as budget denials, and publish complete prices for the models concerned. See [Pricing](/docs/administration/pricing#prices-that-cant-bound-a-request).
- Chat Completions requests that send `max_tokens` now succeed instead of returning `400`.
