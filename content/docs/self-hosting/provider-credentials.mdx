---
title: Provider credentials
description: Give the gateway provider keys as environment references, approve self-hosted endpoints, and use AWS identities for Bedrock.
---

Provider credentials never go through the browser or into the database. A connection in Admin stores a **reference**; you, the operator, supply the secret on the server.

## API keys as environment variables

1. Put the key in an environment variable with a name you choose, for example `OPENAI_API_KEY`.
2. Add the name to `GATEWAY_SECRET_ENV_ALLOWLIST` (comma-separated). The default is empty: no variable can be referenced.
3. Restart. In Admin, the connection's credential is "Secret in an environment variable" with that name.

```sh
GATEWAY_SECRET_ENV_ALLOWLIST=OPENAI_API_KEY,ANTHROPIC_API_KEY,OPENROUTER_API_KEY
OPENAI_API_KEY=…
ANTHROPIC_API_KEY=…
OPENROUTER_API_KEY=…
```

- The gateway can read `OPENAI_API_KEY` and `ANTHROPIC_API_KEY` from files with `_FILE` ([secrets from files](/docs/self-hosting/configuration#secrets-from-files)); other names must be set directly by your orchestrator's secret mechanism.
- An empty `OPENAI_API_KEY` or `ANTHROPIC_API_KEY` stops startup. Leave a key unset rather than empty when you don't use that provider.
- The SMTP password doesn't use this list. From v0.6.0 it has its own, `GATEWAY_SMTP_SECRET_ENV_ALLOWLIST`, and a name on both lists stops startup, so a Platform Admin can't send a provider key to a mail server. See [Configuration](/docs/self-hosting/configuration#email).
- From v0.7.0, listing one of the gateway's own variables stops startup, even on purpose: `DATABASE_URL`, anything starting with `GATEWAY_`, `AWS_`, `PG` or `OTEL_`, the proxy variables, and any variable a gateway setting such as `GATEWAY_SCIM_TOKEN_ENV` names. See [Reserved names](/docs/self-hosting/configuration#reserved-names). Give each provider key its own variable.
- `OPENAI_API_KEY` and `ANTHROPIC_API_KEY` may be listed, but each logs a startup warning: a connection with a custom endpoint that references one sends that key there. Prefer a dedicated name for anything other than the matching cloud provider.
- References and values are never returned by the API or written to logs.
- Removing a name from the allowlist disables every connection that uses it, after a restart.

To rotate a key: create the new key at the provider, update the variable, restart, check that requests work, then revoke the old key.

## Amazon Bedrock

Bedrock uses AWS identities, never keys typed into the gateway:

| Mode | Reference | Operator setup |
|---|---|---|
| Server identity | `aws:default` | The AWS SDK's default credential chain. Prefer a workload role: ECS task role, EC2 instance profile, EKS role. |
| Named profile | `aws:profile:<name>` | A profile in the server's shared AWS config. Add its name to `GATEWAY_AWS_PROFILE_ALLOWLIST`. |
| Assume role | `aws:role:<arn>` | The server identity needs `sts:AssumeRole` on the role, and the role's trust policy must allow it (and require the external ID, if you use one). |

For a PrivateLink endpoint, add its exact HTTPS origin to `GATEWAY_BEDROCK_ENDPOINT_ALLOWLIST`. From v0.6.0 its private address must also be in `GATEWAY_EGRESS_PRIVATE_ALLOW` (the VPC range), or its requests fail with a message naming that variable. Allowlists are checked when a connection is saved and again on every request, so removing an entry and restarting disables matching connections.

Give the identity `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream`, restricted to the models and inference profiles you intend to offer. The gateway ignores `AWS_ENDPOINT_URL` and similar endpoint overrides.

## Self-hosted model servers

Self-hosted servers (vLLM, SGLang, Ollama, other OpenAI-compatible servers) are reachable only at addresses you approve in `GATEWAY_LOCAL_UPSTREAMS`:

```sh
GATEWAY_LOCAL_UPSTREAMS='[
  {"endpoint": "http://models.example.internal:8000/v1", "addresses": ["10.10.1.20"]},
  {"endpoint": "https://gpu.example.internal/vllm/v1", "addresses": ["10.10.1.21"]}
]'
```

- Each `endpoint` is an exact base URL ending in `/v1`, without credentials, query or fragment.
- Each is pinned to its IP addresses: the gateway never looks the name up in DNS. Up to 64 endpoints, 16 addresses each.
- Plain HTTP is allowed only to private addresses (loopback only in development). Metadata, link-local and other special addresses are refused. HTTPS keeps certificate checks.
- From v0.9.0 an approval of an address in a range the outbound policy refuses elsewhere **stops startup**: benchmarking (`198.18.0.0/15`, `2001:2::/48`), IETF protocol assignments (`192.0.0.0/24`), the old 6to4 relay (`192.88.99.0/24`), documentation (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`, `2001:db8::/32`, `3fff::/20`) and AWS's IPv6 metadata range (`fd00:ec2::/32`, over HTTP too). An IPv6 address carrying an IPv4 one (IPv4-mapped, 6to4, Teredo) is judged by the IPv4 address. NAT64 (`64:ff9b::/96`) stays refused. The error names the approval's host, address and category, never a credential. Use the server's real public or private address.
- `/health/ready` still reports `checks.local_upstream_approvals`. It is always `ok` from v0.9.0, because a refused approval stops startup instead; in v0.8.0 it said `warning`.
- A connection may use no authentication, or an `env:` reference sent as a bearer token to that server only.

The dashboard can only choose among approved endpoints; it can't approve a new one.

## Rules for every connection

- Cloud providers use their fixed HTTPS addresses (OpenAI, Anthropic, OpenRouter), or AWS's for Bedrock.
- No redirects are followed, proxy environment variables (`HTTP_PROXY`, `HTTPS_PROXY`) are ignored, and nothing is retried implicitly.
- From v0.6.0 every connection follows the [outbound address policy](/docs/self-hosting/security#the-outbound-address-policy): never metadata, link-local or reserved addresses, and private networks only from `GATEWAY_EGRESS_PRIVATE_ALLOW`. Approved self-hosted servers keep their own pinned approval and need no entry there.
- Callers' API keys are never forwarded to a provider.

Enforce outbound network rules too: the gateway's approval lists are not a firewall.
