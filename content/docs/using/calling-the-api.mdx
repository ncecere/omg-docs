Open Model Gateway speaks the OpenAI API and the Anthropic Messages API, so the official SDKs work with two settings changed: the base URL and the API key.

## The base URL

Your key's page, the **Save your API key** dialog and each model's page show the addresses to use, with copy buttons:

- **OpenAI-compatible base URL**, for the OpenAI SDKs and plain HTTP;
- **Anthropic SDK base URL**, the same address without the final `/v1`, because the Anthropic SDK adds `/v1/messages` itself.

Unless your administrator publishes the inference API on its own address, it is the address you open the dashboard on, plus `/v1`. In these examples it is `https://ai.example.edu`:

| Client | Base URL |
|---|---|
| OpenAI SDKs (Python, Node) | `https://ai.example.edu/v1` |
| Anthropic SDKs (Python, Node) | `https://ai.example.edu` (the SDK adds `/v1/messages`) |
| Plain HTTP | `https://ai.example.edu/v1/...` |

If your installation publishes inference separately, for example at `https://api.example.edu/v1`, the dashboard shows that address instead: use `https://api.example.edu/v1` for the OpenAI SDKs and `https://api.example.edu` for the Anthropic SDKs. A model's page also shows each endpoint's full address, with `wss://` for [realtime](/docs/using/realtime).

## Authentication

Send your [API key](/docs/using/api-keys) as a bearer token:

```http
Authorization: Bearer omg_...
```

`/v1/messages` also accepts Anthropic's `x-api-key` header instead, but not both at once. The workspace comes from the key; there is no header or body field to choose another one. The key never reaches the provider: the gateway calls it with the connection's own credential.

## Model names

Ask for models by their gateway name, such as `example/chat`, not the provider's own id. To see the names your key can use:

- open **Models** in the workspace and copy a model's name, or
- call `GET /v1/models` with the key:

```sh
curl https://ai.example.edu/v1/models -H "Authorization: Bearer $OMG_API_KEY"
```

```json
{"object":"list","data":[{"id":"example/chat","object":"model","created":1760000000,"owned_by":"platform"}]}
```

The list contains models that are enabled, have an enabled route, are available to the key's workspace, and are allowed by the key's own model restriction. Names are matched exactly. A name the key can't use, or one with control characters, answers `404 model_not_found`.

### Streaming

Chat Completions streams token by token. Ask for usage in the final chunk so your own code sees the token counts:

```python
stream = client.chat.completions.create(
    model="example/chat",
    messages=[{"role": "user", "content": "Write a haiku about autumn."}],
    max_completion_tokens=100,
    stream=True,
    stream_options={"include_usage": True},
)
for chunk in stream:
    if chunk.choices and chunk.choices[0].delta.content:
        print(chunk.choices[0].delta.content, end="")
```

Responses and Messages streams work with the SDKs' stream helpers and also send text as it is generated. Tool calls arrive whole, after the text, except on Messages with an Anthropic route, where the stream keeps the provider's order of text, tool and thinking blocks. See [Responses](/docs/api/responses) and [Messages](/docs/api/messages).

### Embeddings

```python
result = client.embeddings.create(
    model="example/embed",
    input=["First document", "Second document"],
)
```

The gateway returns float vectors, or base64 when you ask for `encoding_format="base64"` (little-endian 32-bit floats). The OpenAI SDKs ask for base64 by default and decode it for you, so you don't need to set anything. Batch embedding lines are the exception: they accept `float` only.

## The output maximum

Chat Completions and Responses accept an output maximum, `max_completion_tokens` and `max_output_tokens`, and don't require one. Messages requires `max_tokens`, as Anthropic's API does.

- **Without a maximum**, the gateway uses the model's configured output ceiling: it holds the cost of that many output tokens and sends that maximum to the provider.
- **With a maximum**, the gateway sends yours unchanged. A maximum above the model's output ceiling is refused with `503 provider_configuration_error`.
- Chat Completions also accepts the older `max_tokens` field as the same thing. If you send both, they must be equal, or the request is refused with `400`.

Before a request goes out, the gateway holds the most it could cost against your budgets. A smaller maximum means a smaller hold, so requests are less likely to hit a budget.

## Label sessions and apps for Logs

Two optional headers group and label your requests in [Logs](/docs/using/logs). They are never sent to the provider and never change what the model does.

| Header | Meaning | Limit |
|---|---|---|
| `X-Session-Id` | Groups requests into a session, such as one conversation or one job run. | 1–128 characters |
| `X-Title` | The name of your application. | 1–200 characters |

```python
client = OpenAI(
    base_url="https://ai.example.edu/v1",
    api_key=os.environ["OMG_API_KEY"],
    default_headers={"X-Title": "Course assistant"},
)
reply = client.chat.completions.create(
    model="example/chat",
    messages=[{"role": "user", "content": "Hello"}],
    max_completion_tokens=50,
    extra_headers={"X-Session-Id": "conversation-1042"},
)
```

Without the header, Chat Completions and Responses take a session id from `metadata.session_id`, then `user`, and Messages from `metadata.user_id`. A label that is too long, has control characters or is sent twice is ignored; it never fails the request. Workspace admins can see session ids, and for Teams and Projects so can Platform Admins and Auditors, so don't put personal information in them.

## Retries and errors

The gateway tells the official SDKs which errors are worth retrying:

- **Not worth retrying** carry `x-should-retry: false`, so the OpenAI and Anthropic SDKs don't repeat them: a budget that would be exceeded (`429 budget_exceeded`), unresolved costs blocking a budget (`unresolved_usage`), a model whose token ceilings are above your tokens-per-minute limit (`token_reservation_exceeds_limit`), a price that can't bound the cost (`price_unbounded`), and refusals of something the model or its routes can't do (`unsupported_capability`, `400` or `501`). Retrying these gets the same answer until someone changes the configuration.
- **Worth retrying later**: rate limits and "jobs at once" limits (`429`), and a model whose routes are all cooling down after provider failures (`503`, with a `Retry-After` header).

Each retry your SDK makes is a new request, checked and counted on its own. A request that no route of the model could ever serve, such as a tool feature the provider doesn't support, is refused before anything is held against your budget.

The gateway never retries on its own. If a model has several routes and its administrator allowed failover, a failed attempt can move to another route before any output is returned; never after a stream has started. `/v1/messages` returns errors in Anthropic's shape, without the gateway's error codes; the message says what happened. The full list is in [Errors and limits](/docs/api/errors-and-limits).

## What isn't supported

Each endpoint accepts a documented subset of the vendor's API. Fields outside it are refused with an error instead of being silently dropped. For example: images or audio inside Chat Completions and Responses requests, structured output, reasoning settings on OpenAI-style endpoints, `n` above 1, stored Responses (`store: true`, `previous_response_id`) and hosted or server tools. Responses works without stored state: you can send a response's `output` items back as the next request's `input`. On Messages, base64 images work only on Anthropic routes, and thinking settings take effect only there: other routes accept them and leave them out.

Numbers that must be whole, such as token maximums, must be sent as JSON integers: `200`, not `200.0` or `2e2`.

The [API reference](/docs/api) lists what each endpoint accepts. The same contract is in the repository as an OpenAPI 3.1 document, `docs/openapi/inference.openapi.json`.
